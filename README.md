# perf-lab

给 [qa-lab](../qa-lab) 那个订单服务做压测：找拐点、定位瓶颈、验证优化。

## 为什么自己写压测器

先试了 Locust，gevent 在 Windows 上装了三分多钟没装完，不等了。

我要的东西本来也简单：按阶梯起线程、打固定秒数、每秒记一次快照。Locust 的汇总粒度是按请求类型统计，我想要的是**按秒的时间序列**，好画「QPS 随并发怎么变」这条曲线。150 行自己写，改起来也顺手。

## 怎么跑

前置：qa-lab 的服务起在 8000 端口。

```bash
python prepare.py                 # 库存拉满 + 建压测账号，token 写进 .token
python loadgen.py --stages 10:20,30:30,60:30 --label baseline --token $(cat .token)
python report.py                  # 读 results/*.json，生成 results/report.html
```

`--stages` 的格式是 `并发数:持续秒数`，逗号分隔。

## 压测设计

流量模型按权重选动作：

| 动作 | 权重 | 说明 |
|---|---|---|
| 浏览商品列表 | 10 | 读 |
| 看商品详情 | 6 | 读 |
| 查我的订单 | 3 | 读 |
| 下单 | 1 | 写，扣库存 |

真实电商看的人多、买的人少。全部打下单的话，测的是 SQLite 写锁，不是系统整体吞吐。

每档之间不重启服务，让订单量持续增长——这是故意的，`GET /api/orders` 没有分页，数据量上去它的耗时该跟着涨。

## 结果

基线（单进程）：

| 并发 | 请求数 | QPS | P50 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|
| 10 | 8935 | 446.8 | 18.1 | 40.4 | 54.6 | 0.18% |
| 30 | 11448 | 381.6 | 54.4 | 197.0 | 512.3 | 0 |
| 60 | 7248 | 241.6 | 98.0 | 1110.0 | 1414.9 | 0.03% |

优化后（4 进程）：

| 并发 | 请求数 | QPS | P50 | P95 | P99 | 错误率 |
|---|---|---|---|---|---|---|
| 10 | 17828 | 891.4 | 7.5 | 23.4 | 37.5 | 0.06% |
| 30 | 30104 | 1003.5 | 21.4 | 78.1 | 132.7 | 0 |
| 60 | 16535 | 551.2 | 42.7 | 559.2 | 948.1 | 0 |

## 拐点

基线在 10 并发就到顶了。并发翻 6 倍到 60，QPS 从 446 掉到 241（-46%），P95 从 40ms 涨到 1110ms（27 倍）。

这是排队，不是变慢：单进程 CPU 打满后请求在队列里等着，并发越高等得越久，单位时间处理完的反而更少。

4 进程后拐点后移到 30 并发（QPS 1003、P95 78ms）。再加到 60 并发 QPS 回落到 551，第二个瓶颈出现了。

## 优化

只改了一处：

```bash
python -m sut.run --workers 4
```

Python 单进程一次只能跑一个线程（GIL），加进程是最直接的解法。代价是每个进程各有一份内存里的指标，`/metrics` 只能看到四分之一的量；SQLite 的多进程写锁竞争也更明显。

## 第二个瓶颈

60 并发下 QPS 掉头，按可能性排：

1. **订单列表没分页**：`GET /api/orders` 每次扫该用户全部订单。压测期间订单量一直涨，这条接口的耗时会跟着涨。看 CSV 里 QPS 的逐秒曲线，越到后面越低，跟这个吻合。
2. **每请求新建 SQLite 连接**：`connect()` 每次调用都重新开连接，没有复用。请求量上来后这部分开销不小。
3. **SQLite 写锁**：写操作占比只有 5%，但多进程同时写仍会排队。这一档错误率还是 0，说明还没到锁超时的程度。

下一步按这个顺序试：连接池 → 订单列表分页 → 换 PostgreSQL 再跑一遍同样的阶梯。

## 口径

- QPS = 该档总请求数 ÷ 该档持续秒数
- 延迟是客户端侧测量，含网络和序列化开销
- 压测客户端与目标在同一台机器，客户端本身也会抢 CPU。60 并发那档 P95 上千毫秒，其中有多少是服务端排队、多少是客户端调度，这个方案分不干净。要分干净得把发压机放到另一台
